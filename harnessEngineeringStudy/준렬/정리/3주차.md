### 목표를 세우고 해당 목표를 감각이 아니라 체크리스트로 만든다.

- 좋은 설계는 완벽이 아니라 현 요구사항에 맞는 합리적 선택이다.
    
    → 좋은 설계 = 요구사항 충족 + 변경에 강함 + 읽기 쉬움 + 테스트 가능 + 과하지 않음
    
- 요구사항이  추가될 때 어떤 설계가 더 잘 버티는지 분석
- IF else 기반 설계와 Strategy Pattern 기반 설계 비교

### 좋은 설계의 조건

1. 모듈화 : 레고처럼 부품을 바꿀 수 있게 만들어주는 것
2. 관심사의 분리 : 각자 자기 일만 하게 하는 것 
3. 적응 가능성 : 나중에 바뀔 것을 예상하는 것
4. 직관성 : 처음 보는 사람도 덜 헷갈리게 만들어 주는 것
5. 캡슐화 : 내부 복잡함을 숨기고 버튼만 쉽게 제공

### 그렇다면 CodeCraft 와 같은 AI를 통한 문제 해결은 어떻게 진행해야하느냐?

5단계를 거친다.

1. Explore : 요구사항과 제약사항을 확인
    - 입력 데이터는 어디에서 오는가
    - 출력 형식은 어떻게 되고 무엇인가?
    - 예외상황은 뭄엇인가
    - 확장 가능성
2. Brainstorm : 가능한 설계 옵션에 대해서 trade Off를 고려
    - option a, option b 고려하여 각 옵션에 대한 trade Off 장점 단점 비교
3. Plan : 선택한 설계를 구조화
    - 설계를 선택하고 어떻게 구현할지 계획
4. Implement : 코드 구현
    - 어떤 언어로?
    - 클래스, 메서드
    - enum 데이터 타입, 예외처리
    - 테스트 가능한 구조
5. Verify : 테스트와 엣지케이스 검증

### 기능 요구사항 분석 방법

검증해야하는 순서

1. 기능이 실제로 해야하는 일은 무엇인가
2. 입력 데이터 어떤 형태로 들어오는가
3. 출력은 어떤 형태로 반환되는가
4. 어떤 제약사항과 변경 가능성이 설계를 바꾸는가

→ 기능을 추상적으로 만들면 안됨.

요구사항을 찾는 방법

1. 사용자는 이 기능, 이 시스템으로 무엇을 하려고 하는지
2. 이 시스템 또는 기능이 해야하는 액션
3. 반드시 지원을 해야하는 구현해야하는 흐름은무엇인지
4. 실패하거나 예외가 되는 상황은 무엇인지
5. 지금 구현해야하는 범위와 나중에 확장해야하는 범위 나누기

그리고 입력 출력 검증

deny first rule

- 모르는 요구사항은 그냥 가정하지 않는다.
- 위험한 입력은 허용하지 않는다
- 애매한 정책은 코드 안에 숨기지 않는다.

### 예시 - 배달 수수료 계산기 만들기

1. 요구사항 정리
- **모호한 문제 : 배달 수수료 계산기를 만들어라**
- 입력 : “주문금액, 배달거리, 도시, 고객타입, 날씨, 주문 상태
- 출력 : 기본 배송비, 추가요금, 할인금액, 최종 배송비
- 제약: 음수 금지, 취소 주문 제외, 최종배송비 음수 금지
- 변경 가능성 : 도시별 요금, 날씨별 추가요금, 멤버십 할인, 프로모션 정책
