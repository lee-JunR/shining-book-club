## 시스템 구성 (식당 비유)

| 시스템 구성 | 식당 비유 | 역할 |
| :--- | :--- | :--- |
| **프론트엔드 (Frontend)** | 입구, 메뉴판, 테이블 | 사용자가 직접 보고 상호작용하는 화면 |
| **API (인터페이스)** | 점원 | 사용자의 요청(주문)을 백엔드로 전달하고 결과를 반환 |
| **백엔드 (Backend)** | 주방 (서버) | 전달받은 요청을 처리하고 비즈니스 로직을 수행 |
| **데이터베이스 (DB)** | 창고 | 식재료 및 고객 정보 등 데이터를 영구적으로 저장하고 관리 |

## 코드 크래프트 (Code Craft) 문제 해결 5단계

단순한 알고리즘 풀이를 넘어 시스템 설계, API, 프로덕트 디자인 등 실리콘밸리식 실무 중심의 통합적 문제 해결 접근법입니다.

1. **Explore (탐색):** 요구사항, 제약조건, 입출력 데이터, 예외 상황 등을 명확히 파악하고 질문하여 모호함을 제거합니다.
2. **Breakdown (분석):** 여러 설계 옵션을 비교하고 장단점(트레이드오프)을 분석합니다.
3. **Plan (계획):** 클래스 구조, 데이터 흐름, 책임 분배 등 구체적인 설계도를 수립합니다.
4. **Implement (구현):** 읽기 쉽고, 확장 및 테스트가 가능한 실제 코드를 작성합니다.
5. **Verify (검증):** 요구사항 충족 여부를 확인하고, 엣지 케이스(예외 상황)와 성능을 테스트합니다.

## 좋은 소프트웨어 설계 원칙

좋은 설계란 완벽한 구조가 아니라 **현재 요구사항에 맞는 합리적인 선택(골디락스 범위)**을 찾는 것입니다. 오버 엔지니어링과 언더 엔지니어링을 모두 경계해야 합니다.

### 5대 기본 원칙
* **모듈화:** 시스템을 독립적이고 교체 가능한 부품으로 분리해 유지보수성을 높입니다.
* **관심사의 분리:** 각 모듈이 명확한 단일 역할과 책임을 가짐으로써 상호 간섭을 최소화합니다.
* **적응 가능성:** 요구사항이나 정책 변경에 유연하게 대응할 수 있어야 합니다.
* **직관성:** 처음 보는 사람도 코드와 구조를 쉽게 이해할 수 있어야 합니다.
* **캡슐화:** 내부 복잡성을 숨기고 필요한 인터페이스만 노출하여 사용성을 높입니다.

### 설계 품질 판단의 핵심 기준
* **응집도 (Cohesion):** 모듈 내 관련 데이터와 기능이 뭉쳐있는 정도. **(높을수록 이상적)**
* **결합도 (Coupling):** 모듈 간 서로 의존하는 정도. **(낮을수록 이상적)**

## 요구사항 분석과 실무 적용

* **철저한 요구사항 분석:** 기능의 본질, 입출력 데이터 형식, 필수/선택 여부, 변경 가능성을 사전에 명확히 정의해야 합니다. 불명확한 요구사항 상태로 개발에 들어가면 유지보수가 어려워집니다.
* **예외 상황 대비:** 잘못된 입력값이나 비정상적인 데이터(예: 배달 거리 오류, 음수 페이아웃)에 대한 처리 방안을 설계 단계에서 포함해야 합니다.
* **AI 어시스턴트(클라우드 코드) 활용:** AI가 임의로 가정한 코드를 생성하지 않도록, 요구사항을 명확히 구도화하고 변경 가능성이 높은 부분을 분리한 구체적인 프롬프트를 제공(하네스 엔지니어링)해야 정확하고 확장성 있는 코드를 얻을 수 있습니다.
