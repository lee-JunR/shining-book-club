#  클로드 코드 아키텍처와 객체 지향 설계 원칙 (SOLID)

## 1. 클로드 코드의 서브 에이전트 위임 (Subagent Delegation) 구조

### [1] 개념 및 메커니즘
* **페런트 컨텍스트(Parent Context):** 메인 작업 공간으로서 전체 작업의 맥락, 목표, 히스토리를 총괄적으로 포함합니다.
* **서브 에이전트(Subagent):** 페런트와 분리된 독립적이고 작은 작업 공간입니다. 전체 맥락을 다 알 필요 없이 위임받은 특정 작업만 집중적으로 수행합니다.

### [2] 효율적 컨텍스트 및 세션 관리
* **컨텍스트 과부하 방지:** 서브 에이전트가 수행한 수많은 시행착오, 상세 로그, 실행 기록을 페런트에 모두 넘기지 않습니다. 최종 요약된 결과(Summary)만 반환하여 메인 세션의 컨텍스트 크기를 효율적으로 유지합니다.
* **독립적 격리 환경:** 서브 에이전트는 독립된 공간에서 다양한 시도와 실패를 자유롭게 수행할 수 있으며, 이는 메인 작업 공간에 영향을 주지 않습니다.
* **최소 권한 원칙 (Principle of Least Privilege):** 서브 에이전트는 페런트의 모든 권한을 무조건 물려받지 않고, 작업에 필요한 제한된 권한만 부여받아 안전하게 실행됩니다.

## 2. 코드 설계의 핵심: 책임 분리와 객체 지향 디자인 (OOD)

### [1] 책임 분리 (Separation of Concerns)의 중요성
* 하나의 거대한 함수나 클래스에 모든 비즈니스 로직을 몰아넣는 '신 객체(God Object)' 패턴을 지양합니다.
* 역할과 제어 범위를 명확히 나누어 관리함으로써, 각 책임이 독립적으로 변경될 수 있어 유지보수성이 극대화됩니다.

### [2] 요구사항에서 객체 모델링으로의 변환
* **책임 추출:** 비즈니스 요구사항에서 필요한 행위와 규칙을 도출하여 클래스와 객체로 설계합니다.
* **객체 유형의 명확한 구분:**
    * **Entity (엔티티):** 고유한 식별자(ID)를 가지며 생명주기가 있는 객체
    * **Value Object (Value Object):** 식별자 없이 값 자체로만 의미를 가지는 불변 객체
    * **DTO (Data Transfer Object):** 레이어 간 데이터 전송만을 위해 사용되는 바구니 역할의 객체

### [3] 책임 분리 실무 예시

####  예시 1: 배달비 계산기 시스템
단순히 `calculateDeliveryFee()`라는 하나의 함수로 처리하지 않고 책임을 쪼갭니다.
* **주문 정보 처리 및 입력 검증 레이어:** 입력값의 유효성 검증 (음수 차단 등)
* **기본 요금 산정 레이어:** 거리에 따른 기본 배송비 계산
* **할증 요금 적용 레이어:** 날씨, 특정 시간대, 지역별 프로모션 등 정책 반영
* **할인 및 최종 산출 레이어:** 멤버십, 쿠폰 적용 후 최종 금액 도출 (음수 클램프 처리 등)

#### 🎬 예시 2: 넷플릭스 시청 기록 API
* **이벤트 수집 및 검증 클래스:** 유저의 시청 액션 로깅 및 유효성 판단
* **진행률 계산 클래스:** 전체 러닝타임 대비 시청 chunk 비율 산출
* **정렬 및 필터링 클래스:** 최신순, 이어보기 가능 여부 기준으로 데이터 가공
* **응답 생성 클래스:** 클라이언트 포맷에 맞는 최종 데이터(DTO) 반환

## 3. 시스템 확장성을 위한 SOLID 원칙 적용

| 원칙 | 개념 | 클로드 코드 및 소프트웨어 설계 적용 방식 |
| :--- | :--- | :--- |
| **SRP**<br>(단일 책임) | 클래스나 함수는 단 하나의 변경 이유만 가져야 함. | 하나의 클래스가 배달비도 계산하고 DB에도 저장하는 구조를 방지. 모듈 수정 시 사이드 이펙트 최소화. |
| **OCP**<br>(개방 폐쇄) | 확장에는 열려 있어야 하고, 변경에는 닫혀 있어야 함. | 새로운 할인 정책(예: 눈/비 올 때 할증)이 추가되어도 기존 배달비 핵심 계산 로직은 수정하지 않고 인터페이스 확장을 통해 해결. |
| **LSP**<br>(리스코프 치환) | 하위 타입은 언제나 상위 타입으로 교체 가능해야 함. | 거리 기반 배달비 클래스를 지역 기반 배달비 클래스로 교체하더라도, 상위 서비스 레이어의 동작 메커니즘은 깨지지 않고 유지됨. |
| **ISP**<br>(인터페이스 분리) | 자신이 사용하지 않는 메서드에 의존하지 않아야 함. | 거대한 인터페이스 대신 필요한 기능만 유기적으로 묶은 작은 단위의 인터페이스를 설계하여 불필요한 기능 구현 강요 및 오류 방지. |
| **DIP**<br>(의존성 역전) | 구체화가 아니라 추상화(인터페이스/추상클래스)에 의존해야 함. | 서비스 로직이 구체적인 외부 라이브러리나 정책에 직접 의존하지 않고 인터페이스를 바라보게 한 뒤, 외부에서 구현체를 주입(DI)받아 유연성 확보. |

## 4. 안전한 코드 실행 및 다중 레이어 방어 체계

### [1] 코드 설계와 실행의 엄격한 분리
* **설계 판단과 실행의 분리:** 모호한 요구사항에 대해 임의로 추측하여 실행 권한을 남용하지 않도록 차단합니다.
* 디자인 패턴과 명확한 정책을 사전에 정의하여 코드 본연의 품질과 시스템 안정성을 함께 확보합니다.

### [2] 다중 레이어 제어 (Layered Control)
* **시스템 통제 인프라:** 클로드 코드 내에서는 권한 검증, 위험 행동 차단, 격리된 샌드박스(Sandbox) 환경 실행 등 다중 보안 레이어를 두어 안전장치를 마련합니다.

## 5. 작업 기록(Transcript) 및 세션 관리 기법

### [1] Append-only Transcript (추가 전용 기록 방식)
* 기존에 기록된 데이터를 수정하거나 덮어쓰지 않고, 새로운 타임라인 기록을 뒤에 지속적으로 이어 붙이는 방식을 취합니다.
* 이 구조를 통해 시점 이탈 없이 세션 복원(Restore), 복사(Fork), 되감기(Rewind) 기능을 완벽히 지원합니다.

### [2] JSON Lines (JSONL) 포맷 활용
* **기록 데이터 구조:** 사용자 요청(User), 에이전트 응답(Assistant), 도구 실행 결과(Tool Use/Result) 등을 JSON 형태로 한 줄에 하나씩 기록합니다.
* **이점:** 대용량 로그 스트리밍에 최적화되어 있으며, 특정 행위가 실패했을 때 실패 전 상황으로 세션을 복구하고 재개하기에 매우 용이합니다.
