# AI 스터디 3주차 - 좋은 설계와 요구사항 분석 정리

## 1. 이번 주 핵심

이번 주 내용은 한 줄로 요약하면  
**"좋은 코드는 구현보다 설계와 요구사항 정리에서 시작된다"**는 쪽에 가까웠다.

특히 목표를 감으로 잡는 게 아니라, 체크리스트처럼 잘게 나눠서 구조화하는 과정이 중요하다는 점이 반복해서 나왔다.

***

## 2. 좋은 설계란?

강의에서 말하는 좋은 설계는 완벽한 구조가 아니라,  
**현재 요구사항에 맞는 합리적인 선택**이라고 정리할 수 있었다.

즉 너무 복잡하게 만드는 것도 문제고, 너무 단순해서 변경에 약한 것도 문제다.

좋은 설계의 기준은 대략 이렇게 정리된다.

- 모듈화  
  - 기능을 적절한 단위로 나눠서 수정과 교체가 가능하게 만드는 것.

- 관심사의 분리  
  - 각 모듈이 자기 역할에 집중하게 만드는 것.

- 적응 가능성  
  - 요구사항이 바뀌었을 때도 버틸 수 있게 설계하는 것.

- 직관성  
  - 처음 보는 사람도 구조를 따라가기 어렵지 않게 만드는 것.

- 캡슐화  
  - 내부 복잡함은 숨기고 필요한 인터페이스만 보여주는 것.

그리고 설계 품질을 볼 때는 응집도는 높고 결합도는 낮은 쪽이 좋다는 기준도 함께 나왔다.

***

## 3. Code Craft 문제 해결 흐름

이번 주에는 문제를 바로 구현하지 말고, 먼저 구조화해서 보는 흐름이 중요하게 나왔다.

자료를 종합하면 대략 아래 5단계로 정리할 수 있었다.

1. Explore  
   - 요구사항, 제약사항, 입력/출력, 예외 상황을 먼저 확인한다.

2. Brainstorm / Breakdown  
   - 가능한 설계 옵션을 비교하고 trade-off를 본다.

3. Plan  
   - 어떤 구조로 갈지 정하고 설계를 구체화한다.

4. Implement  
   - 그다음에 실제 코드를 구현한다.

5. Verify  
   - 테스트와 엣지 케이스 검증으로 마무리한다.

결국 구현보다 먼저 탐색과 계획이 앞에 있어야 한다는 흐름으로 이해됐다.

***

## 4. 요구사항 분석에서 중요했던 점

이번 주에서 제일 실무적으로 느껴지는 부분은 요구사항 분석이었다.

기능을 추상적으로 설명하면 사람도 AI도 각자 다르게 해석하게 되기 때문에, 최소한 아래 정도는 먼저 정리해야 한다.

- 이 기능이 실제로 해야 하는 일은 무엇인가.
- 입력 데이터는 어떤 형태로 들어오는가.
- 출력은 어떤 형태로 나가야 하는가.
- 어떤 제약사항이 있는가.
- 실패하거나 예외가 되는 상황은 무엇인가.
- 지금 구현 범위와 나중 확장 범위는 어떻게 나눌 것인가.

또 deny first rule처럼, 모르는 요구사항을 임의로 가정하지 말고 애매한 정책은 코드 안에 숨기지 말아야 한다는 점도 같이 나왔다.

***

## 5. 기억할 포인트

이번 주 내용을 정리하면 아래 두 가지가 핵심으로 남는다.

1. 목표는 감으로 잡는 것이 아니라 체크리스트 형태로 쪼개야 한다.  
2. AI에게도 막연한 요청보다, 목적·제약·예외·확장 범위를 같이 주는 쪽이 더 안정적인 결과로 이어진다.
